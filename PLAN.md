## 2. Architecture decisions

Following spec §7 exactly:

- **Screens are thin.** Expo Router screens call feature hooks/services only; no OCR bridge calls, no SQL, in a screen component.
- **OCR, parsing, persistence, and calculation are separate modules** with no circular imports: `receipt-ocr` → `receipt-parser` → (validated `ParsedReceipt`) → repository layer; `splitting` is pure and independent of both.
- **`ReceiptOcrService` is an interface.** Originally implemented only by `MlKitReceiptOcrService`; as of 2026-07-31 there are three implementations — `MlKitReceiptOcrService` (on-device), `BackendReceiptOcrService` (uploads to the new `server/` backend, which runs a VLM via Ollama), and `FallbackReceiptOcrService` (composes the two: backend first, on-device on any error/timeout). Nothing outside `receipt-ocr/` imports ML Kit or the backend client directly — this is exactly the seam the interface was built for, and neither the parser nor the UI needed to change when the backend was added.
- **Money is integer centavos everywhere**, from parser output through DB columns through split calculation. Formatting to `₱`-strings happens only at the UI boundary.
- **SQLite via Drizzle is the single source of truth**; Zustand only holds transient draft-workflow state (current screen step, in-progress form values) and the active bill ID.
- **All user-facing copy lives in `src/constants/copy.ts`**, matching spec §13/§14 tables verbatim, including placeholder tokens.
- **`server/` is a separate, independent Node package** (own `package.json`/lockfile, installed with `npm` not `pnpm`, deliberately not a pnpm workspace member) providing exactly one thing: `POST /api/ocr`, which proxies an uploaded receipt image to a locally-hosted Ollama vision model and returns transcribed text. It holds no persistent state and stores nothing between requests. See the 2026-07-31 log entry and the spec's amendment note for the full rationale.

## 5. Database schema and migration approach

- Drizzle schema in `src/db/schema.ts` defining the seven tables from spec §9.7: `bills`, `line_items`, `participants`, `item_assignments`, `adjustments`, `adjustment_allocations`, `app_settings`.
- Foreign keys with `ON DELETE CASCADE` from every child table to `bills.id` (and `line_items.id` / `participants.id` where applicable for `item_assignments` and `adjustment_allocations`).
- Indexes on every `bill_id` foreign key column; `sort_order` preserved on `line_items`, `participants`, `adjustments`.
- Money columns (`*_centavos`) are `integer`, never `real`/`float`.
- Migrations generated with `drizzle-kit` and committed under `drizzle/`; applied on app startup via a small migration runner in `src/db/migrations.ts` before any repository call. A startup failure shows the "Database startup failure" copy from spec §14, not a crash.
- All reads/writes go through `src/db/repositories/*`, never directly from screens or feature hooks.

### Milestone 0 OCR spike — passed on a real device — 2026-07-30

The user had a physical Android phone with Expo Go installed and tried to open the project by scanning the `expo start` QR code. That surfaced the actual path to finally clearing this spike, plus several real environment and code gaps along the way.

**Expo Go cannot run this project, full stop — not a version problem.** The error ("Project is incompatible... requires a newer version of Expo Go") is Expo Go's generic message for "this project isn't compatible with me at all," not an actual version mismatch. This project depends on `expo-camera`, `expo-sqlite`, custom config-plugin settings, and especially `@react-native-ml-kit/text-recognition` (a third-party native module) — none of which Expo Go's generic sandboxed client includes. This is exactly why `expo-dev-client` has been a dependency since Milestone 0; a **development build** was always the intended path, it just hadn't been exercised yet.

- **Root cause**: comparing the raw "View extracted text" output against the physical receipt showed every item name grouped together, then every field label, then every number — completely out of visual reading order. ML Kit was returning each table _column_ (name column, price column) as its own block rather than one block per printed _row_. `classifyReceiptLines`'s item-candidate check requires a name and an amount on the same extracted line, so when a row's name and price arrive as two separate, disconnected lines, nothing gets recognized as an item at all.
- **Fix, two parts:**
  1. `MlKitReceiptOcrService.toRect` now falls back to computing a bounding box from `cornerPoints` when `frame` is `undefined` — suspected (not fully confirmed, no way to inspect the native binding's actual on-device behavior directly) that `frame` isn't reliably populated on all devices, similar to how `confidence` is never populated at all (Milestone 0 finding). Cheap, defensible fallback regardless.

### VLM transcription typo breaks VAT-breakdown classification + reconciliation safety net — 2026-07-31

Testing the VLM backend against a real Lian's Lomi House receipt (Philippine BIR format — same merchant as the earlier on-device thermal-receipt findings above) surfaced a new one-character transcription error, plus a decision to add a general backstop rather than keep patching single typos as they turn up.

- **Bug**: Qwen3-VL transcribed the printed `(V)Vatable Sale 388.39` line as `(V)Valable Sale 388.39` (t misread as l). `receiptKeywords.ts`'s `NON_ITEM_INFO_KEYWORDS` only matched the exact string `VATABLE SALE`, so `Valable` fell through `classifyReceiptLines` as an unrecognized `OTHER` line with an amount and non-amount text — i.e. a plain `ITEM_CANDIDATE`. `parseReceipt.ts` added it as a bogus 4th line item worth ₱388.39 alongside the 3 real items (Chicken Chami, Beef Lomi, Lechon Chami, ₱145.00 each = ₱435.00, matching the receipt's real `AMOUNT DUE 435.00`). `diagnostics.warnings` correctly flagged `TOTAL_MISMATCH`, but the bad item itself was never caught or explained.
- **Fix, two parts, deliberately combined** (per the user's explicit request — the keyword fix should catch this exact case correctly as a proper classification, while the reconciliation backstop remains as a safety net for the next unanticipated misspelling):
  1. **Keyword broadening (`receiptKeywords.ts`)** — added a new `isVatBreakdownSaleLine()` structural pattern alongside the existing exact-string `NON_ITEM_INFO_KEYWORDS` list. Rather than requiring an exact spelling of the descriptive word ("Vatable", "Exempt", "Zero-Rated"), it recognizes the _shape_ PH BIR receipts always use for this VAT-breakdown block: a short category code (`V`/`E`/`A`/`B`/`SC`/`PWD`/`Z`/`ZR`/`EX`) with at least one paren still attached (tolerating a dropped paren the same way the existing `(U)Vatable`/`E)VAT-Exempt` test cases already did), then any word, then the literal word `Sale`, then a plausible amount. Requiring the paren (rather than making the whole code prefix optional) is what keeps this from ever matching an ordinary item line that happens to end in "Sale" (e.g. "BURGER SALE 100.00" still classifies as a normal item). Also added `'VAT AMOUNT'` to `NON_ITEM_INFO_KEYWORDS` directly — it's part of the same non-additive VAT-breakdown block (the tax portion of already VAT-inclusive item prices, not a charge on top of them), and without excluding it the fixture would still mismatch even after the `Sale`-line fix, since `Vat Amount 46.61` would otherwise be added as a `TAX` adjustment on top of already-inclusive item prices.
  2. **Reconciliation backstop (`parseReceipt.ts`'s new `reconcileItemsAgainstTotal()`)** — a post-pass that runs after items/adjustments are built, only when `detectedTotalCentavos` is non-null (nothing to guess against otherwise). If the computed total (item subtotal + adjustments) doesn't exactly equal the detected total, it checks whether removing exactly one item would make it match exactly; if so, that item is excluded from `items` and recorded in a new `diagnostics.excludedReconciliationLines` array (mirroring the existing `excludedPaymentLines` transparency precedent — never a silent, unexplainable deletion) plus a new `ITEM_EXCLUDED_ON_RECONCILIATION` warning code. If zero or more-than-one single-item removal would reconcile the total, nothing is removed and the existing `TOTAL_MISMATCH` warning stands exactly as before — no combination-guessing, no multi-item removal. **Tolerance chosen: exact match (0 centavos), not "a cent or two."** Reasoning: the concrete bug this backstops already reconciles exactly once the keyword fix classifies it correctly, so no slack was actually needed for it; and allowing a nonzero residual would leave a confusing state where an item was silently removed _and_ the existing (strict-equality) `TOTAL_MISMATCH` check still fires anyway, since `parseReceipt.ts`'s mismatch check wasn't changed to share the same tolerance. Exact-match-only keeps "we fixed it" and "we couldn't fix it" unambiguous with no other code changes required.
- **New warning code / diagnostics field**: `ParserWarningCode` gained `ITEM_EXCLUDED_ON_RECONCILIATION`; `ParserDiagnostics` gained `excludedReconciliationLines: string[]`; `receiptParser.schemas.ts`'s zod schema updated to match (`receiptParser.schemas.test.ts`'s "accepts real parser output without modification" test round-trips this automatically, no direct edit needed there).
- **New/updated fixtures and tests**:
  - `src/test/fixtures/receipts/lianLomiHouseReceipt.ts` — the real receipt's transcribed text, anonymized per spec §20.4 before committing (customer/cashier names, TINs, MIN/SN/terminal/transaction numbers, accreditation numbers, and the buyer's registered business name/address replaced with synthetic placeholders; merchant name, item lines, quantities, prices, and the exact VAT-breakdown lines — including the "Valable" typo and the "BEFF LOMI" item-name misread — preserved byte-for-byte). Built into an `OcrDocument` via `textToOcrDocument()` (`BackendReceiptOcrService.ts`), the same production code path, per the user's instruction — not `buildOcrDocument()`, since this fixture models the no-geometry VLM path specifically.
  - `src/test/fixtures/receipts/reconciliationJunkLine.ts` — a synthetic fixture covering the reconciliation backstop directly, independent of the keyword fix: an unrecognized "XYZ GARBLED LINE 15.00" line whose removal exactly reconciles an otherwise-mismatched total.
  - `parseReceipt.test.ts` — regression tests for both fixtures (3 real items summing to ₱435.00 with no `TOTAL_MISMATCH`/no bogus VAT item for the real receipt; junk-line exclusion + diagnostics/warning + raw-text-still-visible for the synthetic one), plus two more direct backstop tests: no detected total → never fires, and two equally-fitting removal candidates → ambiguous, so nothing is removed and `TOTAL_MISMATCH` stands.
  - `receiptKeywords.test.ts` — direct unit tests for `isVatBreakdownSaleLine()` (exact spelling, the "Valable" typo, missing-opening-paren, zero-rated/exempt variants, amount-required, and two false-positive guards against ordinary item lines).
  - `classifyReceiptLines.test.ts` — one more end-to-end case confirming the typo'd VAT-breakdown line and the "Vat Amount" line both classify as `INFO`, not `ITEM_CANDIDATE`/`POSITIVE_ADJUSTMENT`.
- **Verification**: `npx jest src/features/receipt-parser` (80 tests, all passing), full `npx jest` (103 tests across 12 suites, all passing — zero regressions), and `npx tsc --noEmit` clean. No new native module or build required — parser-only change, picked up on next Metro reload same as prior parser fixes.
- **Follow-up same day: visible online-vs-fallback indicator.** Added `source?: 'backend' | 'on-device'` to `OcrDocument` (`ocr.types.ts`), set by each `ReceiptOcrService` implementation (never derived after the fact — each implementation tags its own output). `processing.tsx` forwards it as a one-time `ocrSource` route param to `/bill/[billId]/receipt-review` (not persisted — it's a UI hint about how _this_ scan went, not bill data, so it simply won't reappear if the draft is reopened later, same treatment as the existing `imageUri`/`entryMethod` params between capture and preview). The review screen shows it via the existing `StatusBadge` component. 87 tests now (1 new, tagging assertion on `textToOcrDocument`).

### Real-device backend debugging + image preprocessing — 2026-08-03

First real on-device test of the backend path surfaced a chain of unrelated bugs (each looked like the previous one at first), plus a rejected model swap and a new preprocessing step, once the pipeline was actually working end-to-end.

- **Bug 1 — looked like "offline" but wasn't network at all.** User reported the app always showed "Read on-device (offline)" despite having WiFi. Extensive logcat investigation (cleartext-traffic hypothesis, DNS-lookup timing, adb authorization) was a dead end because **neither `FallbackReceiptOcrService` nor `processing.tsx`'s catch block ever logged the actual error** — the fallback swallowed it silently. Added a `console.warn` in the fallback's catch and a `console.error` + on-screen `DEBUG:` text in `processing.tsx` (temporarily; both since reverted/removed once root causes were found). That surfaced the real error: `Unsupported FormDataPart implementation`, thrown in ~17ms — clearly not a network issue.
  - **Root cause**: Expo SDK 57 ships its own fetch/FormData implementation (`expo/src/winter/fetch/convertFormData.ts`) that only accepts a real `Blob` or a Blob-like object exposing `.bytes()` for file parts — it does not understand React Native's classic `{uri, name, type}` object idiom at all (RN's own `FormData.getParts()` still emits that shape; Expo's patched `entries()` passes it through unrecognized, then throws). **Fix**: `BackendReceiptOcrService.ts` now appends `new File(imageUri)` (from `expo-file-system`, which implements the `Blob` interface including `.bytes()`) instead of the `{uri, name, type}` object.
- **Bug 2 — Ollama context-size limit.** Once the upload actually reached the backend, every request failed with `exceeds the available context size (4096 tokens)` — a single receipt image encodes to ~4160+ tokens, over Ollama's default 4096 context window. **Fix**: `ollamaClient.ts`'s `/api/chat` call now sets `options: { num_ctx: 8192 }`.
- **Bug 3 — server never actually read `.env`.** No `dotenv` import existed anywhere in `server/src/`, so `OCR_ENGINE`/`OLLAMA_BASE_URL` silently used their hardcoded fallback defaults regardless of what was in `server/.env` — the whole time. Only surfaced when switching `OCR_ENGINE` to test a different model had no effect. **Fix**: added `dotenv` dependency, `import 'dotenv/config'` as the first line of `src/index.ts`.
- **Bug 4 — Ollama itself not running.** Separately hit `fetch failed` (502) when Ollama had stopped (it was running in a now-closed shell session, not a persistent service). Improved `ollamaClient.ts`'s error message to surface `error.cause` (e.g. `ECONNREFUSED`) instead of the generic, unhelpful `fetch failed`. Added an `ollama` npm script to `server/package.json` (`command -v ollama ... || exec "$HOME/.local/ollama/bin/ollama" serve`) so restarting it doesn't need Claude in the loop.
- **`qwen3-vl:8b` evaluated and rejected as the active engine.** User asked to try the larger variant, hoping for better accuracy. Pulled it (6.1GB) and wired it into `engines.ts` as a new `'qwen3-vl-8b'` `OcrEngine` value. Measured **3m24s** for the same sample receipt that `4b` handles in a few seconds. Ollama's template-selection log showed both tags use the identical `qwen3-vl-thinking` chat template, and `think: false` in the `/api/chat` request does not suppress the hidden reasoning trace for either — confirmed directly (`8b`'s "say only OK" test still emitted a 211-token `<think>` block despite `think: false`). The difference is `8b` reasons far more verbosely for the same prompt (~3300+ decoded tokens vs ~150) and decodes roughly 4x slower per token (~19 tok/s vs ~82 tok/s) — likely a compute-efficiency falloff at this size on this GPU, not a VRAM-fit failure (`ollama ps` showed the smaller model at 100% GPU; the larger one's load/eval characteristics point the same way even though it never stayed loaded long enough to catch mid-request). Net effect: `8b` blows past the 90s fallback timeout on every request, so in the actual app it would silently degrade to ML Kit every single time — strictly worse than `4b` in practice. Reverted `OCR_ENGINE` to `qwen3-vl` (4b); `qwen3-vl-8b` stays wired up as a config option (and the model stays pulled) in case a future Ollama version handles thinking-suppression properly for it.
- **New: server-side receipt image preprocessing (`server/src/ocr/imagePreprocess.ts`).** User asked whether preprocessing (color removal, contrast, resolution) could help recognition. Implemented via `sharp` (new server dependency) rather than client-side `expo-image-manipulator`, which only supports resize/rotate/flip/crop — no color/contrast operations, and adding a library that does would mean a native module and a new EAS build; `sharp` needs neither, just a server restart. Pipeline: resize to a max width (`OCR_IMAGE_MAX_WIDTH` env var, default 1280px, never upscales) → grayscale → `.toColourspace('b-w')` (grayscale alone still encodes a 3-channel sRGB JPEG with R=G=B — confirmed by direct test; explicit colourspace conversion is what actually drops it to one channel) → `.normalize()` for contrast → `.sharpen()` → JPEG output. **Deliberately not a hard black/white threshold** as literally requested — naive binarization clips faint pixels to pure black or white, which can wipe out faint thermal-print text entirely, the exact failure mode this whole effort exists to fix; `.normalize()` stretches existing contrast to the full range instead, without discarding faded detail. Wired into `routes/ocr.ts` inside the existing try/catch (a non-image upload now cleanly returns 502 instead of an unhandled exception — added a regression test for this). 12 server tests now (4 new: grayscale-channel-count, downsize-when-wider, never-upscale-when-narrower, decodable-JPEG-output), all passing; `ocr.test.ts`'s fixtures switched from fake `[1,2,3]` bytes to a real tiny `sharp`-generated PNG since `sharp` (unlike the old raw-passthrough path) rejects non-image bytes. Verified end-to-end against the sample receipt post-preprocessing: transcription still perfect.
- **Verification**: server `npx tsc --noEmit` clean, `npx vitest run` 12/12 passing. Client `npx tsc --noEmit` clean, `npx jest` 103/103 passing throughout (none of these were client-side changes). No new EAS build required for any of this — all server-side or `BackendReceiptOcrService.ts`-internal (JS-only, Metro-reloadable).

After manually testing the full split flow end-to-end, the user asked for two things spec §25 explicitly lists as "Not for MVP Implementation" ("Payment status tracking"): tracking who actually paid toward a bill and showing peer-to-peer settlement ("Person 2 owes Person 1 this much"), plus a fast "just divide the bill by headcount" path. ### Frameless multi-line item receipt (fields split across separate physical lines, not columns) — 2026-08-05

A real ramen-restaurant receipt scan (VLM-transcribed via `qwen3-vl`) surfaced a genuinely new capability gap, not another typo-tolerance patch: this receipt prints each item's fields on **separate physical lines** rather than one row per item —

```
AJI TAMAGO
2@
85.00v
170.00
```

(name, then a bare "N@" quantity marker, then a VAT-inclusive-marked unit price, then the actual line total) — a real, valid receipt layout, correctly transcribed by the VLM in correct top-to-bottom order. The bug was entirely downstream: `BackendReceiptOcrService.ts`'s `textToOcrDocument` never attaches a `frame` to any line, and `normalizeOcr.ts`'s existing `mergeIntoRows` explicitly does nothing for frameless lines (there's no geometry to reconstruct from) — so each of the 4 fragments reached `classifyReceiptLines` in total isolation. The name had no amount (not an item candidate); the bare marker had no letters or amount (`OTHER`, ignored); the marked unit price was the _only_ fragment with both an amount and non-amount text (`"v"`), so it became a bogus item named `"v"` worth the _unit price_ (₱85.00); the bare line total had no letters (dropped). The real item (correct name, correct ₱170.00 total) was never built at all. The same label-then-amount-on-the-next-line shape also broke `Total Due`/`1,655.71`, nulling `detectedTotalCentavos`.

- **Fix 1 — `mergeFramelessLabelContinuations()` (new function, `normalizeOcr.ts`)**, run in `parseReceipt.ts` right after `mergeIntoRows` and before `classifyReceiptLines` (classification depends on the label and its amount sharing one line, same as it already does for single-line receipts). Recognizes a "label line" (has letters, zero amounts) immediately followed by a run of "continuation lines" — either a bare quantity marker (`isBareQuantityMarker`: `2@`/`1@`/`2x`/`x2`-shaped, no other text) or an amount-bearing line whose only non-amount content is empty or a single stray letter (`isAmountPlusAtMostOneStrayLetter`, deliberately not hardcoded to `"v"` — covers whatever single-letter marker the next receipt uses, and deliberately requires _exactly_ one amount so an already-complete two-amount item row is never mistaken for a bare fragment). The run stops the moment a line fails both shapes and gets space-joined into one line, in original order, then handed to the exact same single-line logic every other receipt already goes through. **Guard**: every one of these predicates checks `line.frame !== undefined` first and bails immediately — this pass only ever touches lines with no geometry at all, so the on-device/geometry path is provably untouched (verified with a dedicated fixture asserting geometry-bearing lines pass through `toEqual` the identical input array).
- **Fix 2 — mid-line quantity marker (`MID_LINE_QTY_MARKER`, `detectQuantity.ts`)**. Once reunited, `"AJI TAMAGO 2@ 85.00v 170.00"` has its quantity marker sitting _between_ the name and the amounts, a shape none of the existing leading/trailing quantity patterns cover (they all assume the marker leads or trails the whole line). Added as the last fallback, after every existing pattern has already had a chance to match, so it can never override a more specific existing match (e.g. `"2x BURGER MEAL 240.00"` still resolves via the existing leading pattern, confirmed by a dedicated regression test). Produces quantity `2` and removes just the marker token, leaving `stripAllAmounts` (already existing, unchanged) to clean up the rest — consistent with the existing precedent (`noisyColumnMergeLines`'s `"CHICKEN CHAMI ORD V"`) that a stray single-letter marker is left in the name rather than specially stripped.
- **Fix 3 — "last _plausible_ total" (`parseReceipt.ts`'s `inferTotal`/`inferSubtotal`, refactored into a shared `lastPlausibleAmount` helper)**. Once label+amount lines are correctly reunited, this same real receipt's footer line `"Total No. of ITEMS : 5"` matches the generic `TOTAL` strong-total keyword (it contains the literal word "Total") but carries no money amount at all — and, being literally the _last_ `TOTAL`-classified line in the document (after `Total Due`/`Total Amt Due`), the old "take the last TOTAL line, full stop" logic used it and returned `null` for `detectedTotalCentavos`, discarding an otherwise perfectly good, already-detected ₱1,655.71 total. Fixed by walking `TOTAL`/`SUBTOTAL`-classified lines from the end and using the last one that actually resolves to an amount — a direct, literal reading of spec §11.10's own wording ("last _plausible_ total"). Covered directly with a synthetic fixture (a real total followed by an amount-less "Total No. of ITEMS" footer line).
- **Fix 4 — de-duplicated `Service Charge` in a trailing BIR compliance-recap block (`classifyReceiptLines.ts`)**. This receipt's trailing VAT-breakdown block (`VATABLE`/`VAT EXEMPT`/`ZERO RATED Sales`/`VAT Amount`/`Service Charge`/`Total Amt Due`) restates figures already reflected in the main bill — same non-additive-info category as the existing VATABLE-Sale/VAT-Amount handling — except this time `Service Charge` is caught up in it too, and unlike those, `SERVICE CHARGE` is normally a real, legitimate additive adjustment with no keyword-level reason to exclude it on its own. Without deduplication, `buildAdjustments` (which has no dedup logic) would count it twice. Fixed with a new `findPostPaymentRegionStart()`, the mirror image of the existing `totalRegionStart` cutoff already used for item-candidate eligibility: any `POSITIVE_ADJUSTMENT`/`NEGATIVE_ADJUSTMENT`-classified line after the first `PAYMENT`-classified line _at or after the total region_ is reclassified `INFO` instead. Deliberately anchored on "at/after the total region," never "the first `PAYMENT`-classified line anywhere" — `PAYMENT_KEYWORDS` mixes true bottom-of-receipt tokens (`CASH`, `CHANGE`, `CARD`) with header fields that legitimately appear before every item and every real adjustment (`TIN`, `CASHIER`, `TABLE`, `SERVER`; this exact receipt's own `"Cashier : ..."` header line would otherwise have been the naive "first PAYMENT line" and wrongly suppressed the receipt's real, pre-payment Service Charge). Checked by hand against every existing fixture with a `PAYMENT_KEYWORDS` hit (`simpleReceiptLines`'s header `TIN`/`OR NO` lines, both Lian's Lomi House fixtures' header `CASHIER`/`TIN` lines) — none has a real adjustment positioned after its own post-total payment line, so this generalization doesn't regress any of them; also covered directly with two new unit tests (a real post-payment duplicate correctly suppressed; a real pre-payment adjustment correctly protected despite an earlier header `TIN` line).
- **Arithmetic verified by hand**: item subtotal (₱170 + ₱270 + ₱530 + ₱550 = ₱1,520.00, matching `Total Amount`) + `Service Charge` counted once (₱135.71) = ₱1,655.71, matching `Total Due`/`Total Amt Due`/the `MASTERCARD` payment-line amount exactly. `Net Sale`/`VATABLE`/`VAT EXEMPT`/`ZERO RATED Sales`/`VAT Amount`/`Total Amount` are all non-additive info; only `Service Charge` is a real additive adjustment, and it is now counted exactly once.
- **New fixture**: `src/test/fixtures/receipts/ramenHouseReceipt.ts` — anonymized per spec §20.4 (cashier name, table number, and bill slip number replaced with synthetic placeholders, matching `lianLomiHouseReceipt.ts`'s existing precedent); item names, prices, quantities, and the exact multi-line/split-field structure and typos preserved byte-for-byte. Built via `textToOcrDocument` (the real production path for this bug), matching the existing VLM-fixture precedent.
- **Tests**: `normalizeOcr.test.ts` — 6 new direct unit tests for `mergeFramelessLabelContinuations` (the 4-line item shape, a label+next-line-amount pair, a run that correctly stops before the next unrelated item, geometry-bearing lines proven untouched, an ordinary complete line left alone, and a label line with no qualifying continuation left alone). `detectQuantity.test.ts` — 3 new tests for `MID_LINE_QTY_MARKER` (the mid-line `@` marker, the mid-line `x` marker, and confirmation it never overrides an already-matching leading pattern). `classifyReceiptLines.test.ts` — 2 new tests for the post-payment adjustment-suppression logic (real post-payment duplicate suppressed; real pre-payment adjustment protected despite an earlier header `TIN` line). `parseReceipt.test.ts` — the full `ramenHouseReceipt.ts` regression (4 correct items with correct totals and no unit-price bogus item, `detectedTotalCentavos` = ₱1,655.71, exactly one `SERVICE_CHARGE` adjustment worth ₱135.71, arithmetic reconciles with no `TOTAL_MISMATCH`) plus a synthetic "last plausible total" regression for Fix 3.

### GrabFood delivery + North Park Noodles dine-in receipts: 5 parser bugs from manual transcription review — 2026-08-06

Two real receipt photos (a GrabFood delivery receipt and a North Park Noodles dine-in receipt) were manually transcribed and diagnosed against the parser via scratch-test runs. **The source images are no longer available** — the two new fixtures below are explicitly labeled reconstructed/representative reproductions of the structural bugs found, not byte-exact real-receipt transcriptions (contrast with `lianLomiHouseReceipt.ts`/`ramenHouseReceipt.ts`, which are byte-for-byte). Five confirmed bugs, all fixed:

- **Bug 1 — leading quantity not extracted when the item code starts with a digit (`detectQuantity.ts`)**. GrabFood lines like `3 2PC BGRSTKSPR @202 606.00V` and `1 1PC CKNJOY 100.00V` have a remainder (after the leading quantity digit) that itself starts with a digit-leading item code ("2PC", "1PC"), not a letter — `LEADING_QTY_PLAIN`'s original letter-only alternative missed both entirely, so quantity silently defaulted to 1 and the leading digit stayed glued into the item name. Fixed by widening `LEADING_QTY_PLAIN` with a second alternative: 1-3 digits immediately followed by 1-3 letters and a word boundary (`\d{1,3}[A-Za-z]{1,3}\b`). This can't create a new ambiguity with two adjacent bare numbers ("2 3.00") because a bare amount's leading digits are always followed by "." not a letter, which the new alternative requires.
- **Bug 2 — stray marker suffixes not stripped from item names (`parseReceipt.ts`)**. Every GrabFood item retained a glued trailing VAT-inclusive marker letter (`606.00V` → name kept a trailing "V") and/or a bare `@<digits>` unit-price marker with no decimal point (`@202` — `detectAmounts` never touches it at all, by design, since spec §11.5's amount pattern requires exactly 2 decimal digits to correctly exclude OR numbers/TINs/table numbers). Fixed by extending `stripAllAmounts()`: for each amount removed, also consume a single letter _glued directly_ to it (no separating whitespace — reusing the same "amount plus at most one stray letter" shape as `normalizeOcr.ts`'s `isAmountPlusAtMostOneStrayLetter`, applied here to name cleanup instead of line-merging), plus a separate `.replace(/@\d{1,4}\b/g, ' ')` pass for the bare unit-price marker. The "glued, no space" requirement is what keeps this from regressing the existing `noisyColumnMergeLines` fixture, whose marker letter is _space-separated_ ("145.00 V") and must stay in the name — confirmed with a dedicated regression test.
- **Bug 3 — VAT-breakdown "informational" lines wrongly become real TAX/adjustment lines or phantom totals (`receiptKeywords.ts`, `classifyReceiptLines.ts`)**. Same bug family as the two 2026-07-31/08-05 VAT-breakdown entries above, two more uncovered label variants: (a) GrabFood's `VAT-Exempt Sales 0.00` and North Park's `VAT-EXEMPT SALES 675.89`/`VATable Sales`/`Zero-Rated Sales` print the breakdown block with **no parenthesized category code at all** and pluralize "Sale" as "Sales" — the existing code-anchored `VAT_BREAKDOWN_SALE_LINE_PATTERN` hard-required the paren, and its `\bale\b`-style boundary could never match plural "Sales" (a word boundary can't sit between "e" and a following "s"). Fixed by adding a second, narrower branch to the same pattern: no code required, but the descriptive word must literally be one of the known VAT category words (`Vatable`/`VAT-Exempt`/`Zero-Rated`) — anchoring on the literal category word instead of the code is what keeps this from also accepting an arbitrary "BURGER SALES 100.00"-shaped false positive. "Sale" is now `[s5]ales?` (optional plural) in both branches. (b) North Park's `VAT Tax 53.14` and `Total Tax 53.14` — two more spellings of the already-included tax portion `isVatAmountLine`'s "Vat Amount" already covers a different way. `VAT Tax` fell through to the generic `VAT`/`TAX` positive-adjustment keyword; `Total Tax` is the more dangerous one, since it contains the bare word "Total" and was being swept into `STRONG_TOTAL_KEYWORDS`' generic `TOTAL` match, producing a phantom second total candidate (`MULTIPLE_TOTALS_FOUND`) instead of being recognized as information. Fixed with a new `isVatTaxBreakdownLine()` recognizer (whole-line match on `(Vat|Total) + Tax` + amount, mirroring `isVatAmountLine`'s discipline), wired into `classifyByKeyword()` in the same INFO-check group that already runs _before_ the subtotal/total/adjustment keyword checks — this ordering is what stops "Total Tax" from ever reaching the `TOTAL` branch.
- **Bug 4 — explicit printed negative sign gets forced positive (`parseReceipt.ts`'s `buildAdjustments()`)**. North Park's `Sales SC: (G2/S2) -757.00` (reconstructed here at a smaller, bill-consistent magnitude) matches the `SC` positive-adjustment keyword (normally Service Charge) but is a senior-citizen-discount-style deduction printed with an explicit "-". The old logic took `Math.abs()` and re-signed purely from the classified kind (`POSITIVE_ADJUSTMENT` → force positive), discarding the printed sign entirely — a rule that was built for the _opposite_ real-world case (receipts that print a discount as a bare positive figure with no minus sign at all, which still must resolve negative). Fixed with one unified rule, documented in a comment: an explicit sign already folded into `amount.centavos` by `detectAmounts` (which only ever produces a negative value when the source text actually carried a "-"/parens) always wins over the keyword-inferred sign; the keyword-inferred sign is only a fallback for when the source has no explicit sign at all. Verified both directions stay correct: a sign-less `DISCOUNT 20.00` still force-negatives (original fix, unregressed), and a sign-bearing `POSITIVE_ADJUSTMENT`-keyword line now correctly resolves negative (new fix).
- **Bug 5 — parenthetical quantity marker not extracted (`detectQuantity.ts`)**. North Park's `DR10 HONEY LEMONADE (2 @ 176.00` has a parenthesized quantity marker ("(2 @") between the item name and the amount — a shape the existing `MID_LINE_QTY_MARKER` (bare "2@"/"2x", no parenthesis) didn't recognize, leaving quantity at 1 and "(2 @" glued into the name. Fixed with a new `MID_LINE_PAREN_QTY_MARKER` (`\s\((\d{1,2})\s*@\s*(?=\d)`), checked last, same spirit and ordering discipline as `MID_LINE_QTY_MARKER`.

### Groq performs full receipt extraction, not just transcription — 2026-08-11 (same day as the Groq switch above)

User-directed follow-up to the Groq switch above: rather than Groq transcribing raw text for the existing deterministic parser (`src/features/receipt-parser/`) to classify, Groq now classifies items/totals/adjustments itself and returns them as structured JSON directly. **Explicitly flagged before implementing**, same treatment as every other spec deviation in this log: this crosses the specific line both the 2026-07-31 and the same-day Groq-switch amendments drew when first allowing an LLM into this pipeline ("the model only ever transcribes text; it never decides what's an item, a total, or a discount") — logged as a second same-day spec Amendment rather than silently absorbed. Real trade-off, not free: money-correctness risk (a misclassified total/dropped item) is no longer checked against the deterministic parser's 300+ tests for this path — mitigated by keeping the existing pre-save receipt review screen (spec §13.9) as the actual correctness backstop, same as it already was for on-device OCR's own occasional misreads.

- **Prompt** (`server/src/ocr/prompts.ts`'s new `RECEIPT_EXTRACTION_PROMPT`, replacing `RECEIPT_TRANSCRIPTION_PROMPT`) — asks for one JSON object: `merchantName`, `receiptDate` (YYYY-MM-DD), `items` (name/quantity/lineTotalCentavos), `adjustments` (type/label/amountCentavos, negative for discounts), `detectedSubtotalCentavos`, `detectedTotalCentavos`, and `rawText` (still a full best-effort transcription, kept for the existing "view raw text" debug affordance and stored as `rawOcrText` on the bill row same as before). Explicit rules: integer centavos only (never decimal pesos), exclude non-item info/payment lines from `items`, exclude a VAT/tax breakdown line that would double-count an amount already covered elsewhere, null for anything undeterminable.
- **Verified directly against the real Groq API before writing any code** (same discipline as the reasoning-suppression finding below): sent the actual `assets/receipts/sample-receipt.png` through a hand-built request with `response_format: {type: "json_object"}` — got back perfectly correct structured output (every item name/quantity/total, VAT/service-charge/discount adjustments with correct signs, subtotal/total, merchant name, and an ISO-formatted date converted from the printed `01/15/2026`) on the first try.

The client (`BackendReceiptOcrService.ts`) validates the response _again_, independently, against its own copy of the same lean schema — a network response is untrusted input regardless of what the server already did (spec §7).
- **`ReceiptOcrService` interface changed**: `recognize()` now returns `{ receipt: ParsedReceipt, source: 'backend' | 'on-device' }` instead of a raw `OcrDocument` — every implementation now hands back an already-fully-classified `ParsedReceipt`, not text for `processing.tsx` to run through `parseReceipt()` afterward. `MlKitReceiptOcrService` still runs the unchanged deterministic parser internally (ML Kit has no reasoning of its own); `BackendReceiptOcrService`'s new `groqExtractionToParsedReceipt()` adapts Groq's lean JSON onto the same `ParsedReceipt` shape instead — filling in per-item `confidence: null`/`source: 'OCR'`, each adjustment's spec-F-014 default allocation method (reused directly from `features/adjustments/defaultAllocationMethod.ts` rather than yet another copy of that table), and a reconciliation-only (arithmetic, not reclassification) set of warnings (`NO_ITEMS_DETECTED`/`NO_TOTAL_DETECTED`/`SUBTOTAL_MISMATCH`/`TOTAL_MISMATCH`) — the parser-only warning codes that have no LLM-path equivalent (`MULTIPLE_TOTALS_FOUND`, `LOW_CONFIDENCE_LINES_USED`, `PAYMENT_LINE_EXCLUDED`, `ITEM_EXCLUDED_ON_RECONCILIATION`) are simply never raised for this path. `FallbackReceiptOcrService`'s own logic didn't need to change at all — it was already source-agnostic.
- **`parseReceipt.ts` itself is untouched** — it's still the deterministic classifier for the on-device fallback, and all of its existing 300+ tests still cover exactly that path. `textToOcrDocument` (the "flatten transcribed text into a frameless OcrDocument" test helper `BackendReceiptOcrService` used to expose for building the several real-device regression fixtures) moved to `src/test/fixtures/receipts/buildOcrDocument.ts` — it's now purely a test-fixture builder, since the backend itself no longer deals in raw transcribed text at all.
- **Tests**: server gained `receiptExtraction.schema.test.ts` (7 cases) and a rewritten `ocr.test.ts` (mock moved to `groqClient.js`'s new export name; added cases for invalid-JSON and schema-mismatch → 502, distinct from a Groq-call failure) — 20/20 passing. ### Real-device finding: Groq misread the printed total on a real thermal receipt — 2026-08-11

First real-receipt test of the full-extraction Groq backend (a North Park Noodles-style dine-in receipt: Table T9, 4 items totaling ₱1,520.00, ₱135.71 service charge, ₱1,655.71 total due). Items, quantities, and the service charge all extracted correctly — but `detectedTotalCentavos` (and the `rawText` transcription of the same figure) came back as ₱1,355.71 in all three places the receipt actually prints ₱1,655.71 (Total Due / MASTERCARD payment line / Total Amt Due), a `6`→`3` misread on the thermal print. Confirmed by hand: ₱1,520.00 (items) + ₱135.71 (service charge) = **₱1,655.71**, matching the photographed receipt exactly.

- **This is exactly the risk flagged in this same day's "Groq performs full receipt extraction" entry above**: a misread that isn't caught by the deterministic parser's tests, since that parser isn't in this path anymore. It came back identical in all three on-receipt occurrences of the figure — not because they were each independently misread the same way by chance, but because this is one reasoning pass over the image, not three independent per-line transcriptions the way the old text-only backend worked.
- **Blast radius, confirmed by re-reading `receipt-review.tsx`**: the app's actual split math (`computedTotalCentavos = itemSubtotalCentavos + adjustmentTotalCentavos`) does **not** use `detectedTotalCentavos` at all — that field only feeds the existing "detected total vs. computed total" cross-check banner (spec's pre-existing reconciliation UI, not something added for Groq). So this bug would have surfaced there as a ₱3.00 mismatch warning, not a corrupted split — but the "Detected total" reference figure shown to the user, and which direction the mismatch banner points, were both wrong.
- **First fix attempt (insufficient on its own)**: added a self-verification instruction to `RECEIPT_EXTRACTION_PROMPT` — check `detectedTotalCentavos` against items+adjustments arithmetic before answering; re-examine printed digits (noting 3/5/6/8 as a common thermal-print confusion) rather than trusting the first reading, when the two disagree. Regression-tested clean against the known-good `assets/receipts/sample-receipt.png`, but **re-tested against the real receipt once the user saved it to `server/sample_receipts/receipt_ramen.png` and still failed** — same `1,355.71` misread, unchanged.
- **Root cause of why the first fix couldn't work**: the model's own adjustments list was itself wrong, which broke the self-check's arithmetic before it ever got to the digit-legibility question. This receipt's item unit prices carry a trailing `v` (`85.00v` etc.) — VAT-inclusive pricing, the exact `noisyColumnMergeLines`/`ramenHouseReceipt` marker convention this app's old deterministic parser already had dedicated handling for (`PLAN.md`'s 2026-08-05 entries). Groq extracted a separate `"VAT Amount"` adjustment (₱162.86) on top of those already-VAT-inclusive item prices — double-counting VAT. Its own arithmetic was then items (₱1,520.00) + VAT (₱162.86) + service charge (₱135.71) = ₱1,818.57, which matched _neither_ the true total (₱1,655.71) _nor_ its misread one (₱1,355.71) — so there was nothing consistent for the self-check to converge on.
- **Second fix**: rewrote the adjustments rule in `RECEIPT_EXTRACTION_PROMPT` to name this exact pattern explicitly rather than relying on generic "don't double count" phrasing — Philippine BIR-format receipts print a `VATABLE`/`VAT EXEMPT`/`ZERO RATED Sales`/`VAT Amount`/`Net Sale` recap block that only restates how an _already-charged_ total breaks down, spelled out as non-additive even though `VAT Amount` looks like a tax; the `v`-suffix VAT-inclusive-pricing tell is named directly; and a charge printed twice (this receipt's `Service Charge` appears once before `Total Due` and again inside the recap block) must be counted once. Reworded the total self-check to explicitly try "did I wrongly include a non-additive breakdown line" before "was a digit misread," in that order.
- **Verification, against the actual real receipt this time**: `curl`'d `server/sample_receipts/receipt_ramen.png` through the live dev server. Adjustments now correctly contain only `Service Charge` (₱135.71) — `VAT Amount` correctly excluded. `detectedTotalCentavos` is now **₱1,655.71**, matching the photograph exactly, and even `rawText`'s transcription of that figure self-corrected to `1,655.71` in all three places (Total Due / MASTERCARD / Total Amt Due) instead of `1,355.71` — confirming the digit-misread symptom really was downstream of the double-counted-VAT arithmetic being wrong, not an independent problem needing its own separate fix. Re-ran the known-good sample receipt afterward (still correct — VAT still applied there, since that receipt's VAT is a genuine separate charge with no `v`-inclusive marker, confirming the new rule is contextual, not a blanket "ignore VAT" regression) and the full server suite (`npx vitest run`, 20/20; `npx prettier --check`, clean).

### Real-device finding: zero-priced item omitted, then a low-res photo exposed the total-vs-arithmetic tension directly — 2026-08-11

Third real receipt tested (a low-resolution photo, `server/sample_receipts/reciept_lowres.png`, of a KOGI BULGOGI dine-in bill: Free Banchan ₱0.00, 4 priced items, ₱84.40 service charge, ₱1,139.40 bill total). Verified against the photo directly (not just the extraction's own `rawText`, this time — read the receipt image myself and compared line by line):

- **Bug 1 — a real, printed ₱0.00 line item ("Free Banchan") was silently omitted.** Every other item/adjustment/total was correct. Cause: `RECEIPT_EXTRACTION_PROMPT`'s items rule said "a price actually charged," which a 0.00 complimentary item doesn't satisfy despite being a real printed line. **Fix**: reworded to explicitly keep a 0.00 item ("0 is a valid lineTotalCentavos") rather than treating a free item as not really an item.
- **Bug 2 (surfaced by the Bug 1 fix, on this same low-res photo) — `detectedTotalCentavos`/`detectedSubtotalCentavos` came back ₱20.00 too high** (₱1,159.40/₱1,075.00 vs. the correct ₱1,139.40/₱1,055.00) even though the model's own items+adjustments arithmetic already summed to the _correct_ ₱1,139.40 — the same "self-check disagrees but doesn't resolve it" shape as this same day's earlier `receipt_ramen.png` finding, on a harder (lower-resolution) photo. The existing self-check instruction told the model to "re-examine the digits" on disagreement but didn't say what to do if it re-examined and still preferred its (wrong) total-line reading over its own (correct) itemization.
- **Fix 2, a real policy decision, not just a wording tweak**: across all three real receipts tested today, the model's line-by-line itemization + adjustments consistently summed correctly, while the single standalone printed total/subtotal figure was the one repeatedly misread (this entry, and the two `receipt_ramen.png` misreads in the two entries above). Changed the self-check's resolution rule from "re-examine and use your judgment" to an explicit priority order: when items+adjustments arithmetic disagrees with the read total and no double-counted/missing charge explains it, **trust the items+adjustments sum over the standalone total line** — reasoned in the prompt itself as "each item amount can be individually checked against its own printed line, while the total is one isolated figure with nothing else to cross-check it against." This does trade away some of `detectedTotalCentavos`'s value as a fully independent check (see the two entries above's discussion of why that mattered) — accepted deliberately, since an independent check that itself has the highest error rate of anything in the payload was providing negative value, not a safety margin.
- **Verification**: re-tested all three real/synthetic receipts collected so far after the fix — `reciept_lowres.png` now correctly includes Free Banchan (₱0.00) and reports ₱1,139.40 (both subtotal and total now match items+adjustments and the printed Bill line); `receipt_ramen.png` unregressed (still ₱1,655.71, VAT still correctly excluded); `assets/receipts/sample-receipt.png` unregressed (VAT/service charge/discount all still correctly applied as real adjustments there, confirming the priority change didn't make the model stop trusting a printed total when it actually agrees). One transient `429` (Groq's free-tier 8,000 TPM rate limit, from this session's volume of manual test calls) hit mid-verification — not a bug, resolved by retrying a few seconds later. Server suite (`npx vitest run`, 20/20) and `npx prettier --check` still clean.

### Post-MVP feature: Trips (multi-bill splitting with a shared roster) — 2026-08-18

User request: split several bills from the same outing (e.g. lunch, then coffee, then dinner) among the same group of people without re-typing names each time, settling up once at the end instead of after every bill.
